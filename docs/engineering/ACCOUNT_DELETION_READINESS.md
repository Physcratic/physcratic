# B5 account deletion and B6 activation

11 November 2026. PR140 implements the owner's approved limited evidence exception. Code readiness and Production activation are separate decisions. `ACCOUNT_DELETION_ENABLED` defaults OFF. Native Better Auth deletion remains disabled. `PRACTICE_CHECKS_ENABLED` remains default OFF. No migration, grant, provider configuration, Terms or feature flag is activated by this work.

## User lifecycle

Settings exposes deletion only behind the server flag. A verified user must sign in within ten minutes, enter the current password and type `DELETE MY ACCOUNT`. Passwordless accounts must establish a password and sign in again. The displayed-account header only rejects a stale account view. SQL obtains identity, actual unexpired session and current credential proof from locked auth rows. Persistent password checks are bounded before password hashing. Origin checks, strict JSON, bounded bodies and private no-store responses apply.

A browser-generated 256-bit request capability survives an interrupted acknowledgement without persisting the password. The database receipt contains a random deletion ID, completion state and pending object count. It cannot read personal data or delete another account. Reusing a nonce under another authenticated account is rejected. Receipt recovery refreshes current sign-in without signing out a newly switched account. Only a confirmed complete receipt can be forgotten. Local practice/authored recovery for the original account is removed without touching another account's work.

`0018_account_deletion.up.sql` is additive. One privileged transaction removes credentials, provider links, sessions, profiles/preferences/favorites, private drafts, personal authored/practice answers/reveals, legacy solution/evidence/rating/archive/contest ownership and unnecessary private records. Published revisions, supporting media and other students' records survive. The original user is physically removed. A fixed shared Deleted user principal cannot acquire credentials, provider links or sessions and contains no closed-account identity.

Ordinary immutable history stays immutable. Private transaction-local exact OLD/NEW row permits allow only the eraser's chosen mutations. Privileged functions have catalog-first, trusted-schema, pg_temp-last search paths and no PUBLIC execute, except the harmless exact-permit boolean probe required by existing invoker triggers. No triggers are disabled and no historical migrations/FKs are rewritten. New FK-free writes lock a live owner through commit so stale authenticated writes cannot recreate deleted private rows.

Database success is distinct from object cleanup. The same transaction registers private author/profile/medal object keys in an outbox. Registered namespaces are checked in SQL and again before provider calls. Operator cleanup claims use bounded leases, lease-token acknowledgements, generic failure records and durable backoff. Provider deletion must be idempotent. No user-supplied URL is fetched. There is no claim of an atomic database/blob transaction.

## Limited evidence and publication rights

No default policy approval or retention interval is installed. Every enabled execution first requires an explicitly approved `account_deletion_policy` row. It records purpose, legal basis, responsible operator, access rules, review/disposal criteria, approval reference/date and approved receipt/evidence/review/access limits.

A departing account with associated mixed-person evidence receives a review-required response and reference, not a success receipt. Verified current admin staff use `/api/admin/account-deletion` with recent sign-in and current password. `inventory` identifies relationally associated cases. `identify` can link one exact primary key in a fixed allowlist when a privacy request discovers another case record. It requires a documented access purpose and cannot query arbitrary tables. This is operator adjudication, not a claim to detect arbitrary personal information automatically.

`prepare` binds the source snapshot digest, selects only necessary retained fields, sets reviewed source replacements, documents necessity/legal basis/responsible operator/review and disposal criteria, and sets explicit bounded review/expiry dates. `erase` cannot retain fields. A second admin, distinct from subject and preparer, must `approve`. Source changes require renewed adjudication. Case keys, independent ownership and moderation states cannot be changed by a replacement. Missing approval prevents cleanup. Approved retained data is held in a private vault while the ordinary case source is minimized. The subject link is cleared atomically. Access is logged and denied when restricted, overdue or expired. Operators can `restrict` or independently `dispose`; disposal and expiry remove the whole vault row, including free-text metadata and operator identifiers.

Published work is transferred to Deleted user. Existing continuing display requires an explicitly reviewed `account_deletion_publication` decision with rights basis and review reference. Without it the problem is archived and its public pointer cleared, while revisions, prior pointer/state and other students' dependencies remain. This does not require new licence acceptance and does not prevent personal deletion. Rights review and any later display restoration must be performed by an authorized operator against the retained revision under a valid existing rights basis. Do not infer consent or automatically restore public display. The [prospective licence proposal](PUBLICATION_LICENSE_PROPOSAL.md) remains inactive and subject to legal review.
