# Explicit authored solution access — Phase 6C-A

Backend only. Solutions remain private by default. Migration0005 creates no grants for existing publications and changes no sealed worked-solution content or historical attempts. There is no solution-view UI/preload/public-reader/grading-response disclosure. The existing no-reveal-v1 contract continues to mean that submitting or receiving a grade does not automatically unlock private material.

## Author authorization

Verified owner endpoints:

- `GET /api/authored-problems/drafts/[problemId]/solutions/[partId]/permission?revision=<uuid>` reads metadata for an owned immutable revision/part. An absent permission returns version0/enabled=false. Includes unique native solution-image IDs and available revision solution-PDF IDs for deliberate selection; never numeric/expression marking keys, tolerances or hints.
- `PUT` uses the same path **without a query string** (revisionId is JSON-only), and takes strict JSON `{revisionId,version,enabled,mediaIds?,expiresAt?}`. version is the previous permission version (0 initially), **not** the draft version. mediaIds defaults[]; expiry defaults null. Same-origin protection, shared60/min author-write bucket,20KB actual body/5s read deadline, SQL5s/lock2s/idle10s limits apply.
- Enabling requires that exact revision be the current publication, meaningful worked-solution content or a selected PDF, and explicit approval of **every image in that part's worked solution**. Partial image approval is rejected; text/math blocks are approved as a whole part. Hint-only/other-part images, statement assets, wrong-problem/history-only IDs and unregistered/unready files are denied.
- PDFs were revision-wide in the sealed Phase4 document. A selected solution PDF gains an explicit per-part association through the new permission-media table. No revision PDF is automatically shared. The author authorizes the complete selected file for that part and is responsible for its contents; this feature does not parse/classify PDF pages. A PDF-only worked solution is supported. Raw Blob paths/URLs/credentials are never returned.
- Every successful change rotates a server UUID authorization generation and increments the optimistic permission version. Concurrent same-version writes yield one success and one409; an ambiguous author write must be re-read before changing it again. Expiry is checked against database time. Version arithmetic is checked against the PostgreSQL integer bound; it never wraps.
- Revocation is `{enabled:false,mediaIds:[],expiresAt:null}` and may target an owned historical/unpublished revision too. It rotates generation/removes bindings; enabling a hidden/old revision is denied. Permissions cannot be deleted through SQL/API. Unpublication immediately denies future student requests. Previously delivered/downloaded information cannot be recalled.

## Explicit student reveal

`POST /api/authored-problems/[problemId]/solutions/[partId]/view` accepts only `{revisionId}`. It requires a verified server session, configured same-origin request and the exact current published revision/part. **No prior attempt, correct answer or grade is required.** Each request charges the existing persistent60/min student total bucket; it does not consume the20/min submission-specific bucket or100/day attempt quota. There is no separate unbounded reveal rate allowance.

The service selects only `private_part.data->'solution'`, validates native blocks, verifies all approved media and returns an explicit allowlist: problem/revision/part IDs, worked-solution blocks, approved media IDs/types/local proxy URLs, and the caller's reveal receipt `{id,createdAt,replayed,policy:'explicit-solution-v1'}`. It never selects/serializes marking keys, expected expressions, tolerances, hints, other private parts, private storage locations or diagnostics.

Before any solution response, commit an immutable ledger event unique on `(user,revision,part,authorization generation)`. Repeated/concurrent requests within the same valid grant return the same event/timestamp without another event; no caller-supplied idempotency identity is needed. There is no automatic POST on reads, grades or media GETs. **Permission/publication/expiry are rechecked before reusing a receipt**, so replay cannot resurrect revoked access. Regrant/new generation requires a new explicit request/receipt. Commit failure returns generic503 with no solution data; a lost committed response conservatively counts as assistance even if delivery cannot be confirmed.

## Private solution-media proxy

`GET /api/authored-problems/[problemId]/solutions/[partId]/media/[mediaId]?revision=<uuid>` is distinct from the unchanged author/statement media proxy. A verified caller must have revealed this exact part under its **current authorization generation**. Permission alone, another student's receipt or another part's receipt is insufficient. The file must be explicitly approved and bound to that exact revision/problem/part, with solution-image/solution-pdf purpose and ready registry state.

Every GET checks current publication, live permission/generation/expiry, own ledger and approved binding. The server holds publication/permission locks while fetching and fully consuming at most3MiB from existing private Vercel Blob storage, with a4s whole-read deadline and exact registered byte-size check. Failed/oversized/truncated/stalled reads do not disclose bytes; pending/late streams are canceled. Expiry is checked again after storage reads. Response bytes are buffered before commit/response so revocation has an explicit request ordering. An already-authorized response may finish transferring after a later revocation; recall is not promised.

All JSON/media responses are private/no-store, Vary:Cookie and nosniff; media also uses same-origin CORP, sandbox/default-src-none CSP and no-referrer. PDFs download with a generic filename. No redirects/signed Blob URLs/bearer capability in URLs/public caching is added. The existing generic media proxy remains owner-only for all solution assets, even after an explicit reveal. Historical revision bindings continue to protect storage cleanup.

## Assistance and transaction ordering

**Conservative multipart policy:** any committed explicit student reveal of any part assists every subsequent **new** attempt by that user on the same immutable revision, including other parts and all four grading outcomes. This is intentionally broader than per-part help. Revocation/expiry does not erase assistance; a new revision starts independently. It measures this app's student reveal ledger, not offline knowledge or author-editing access.

- Reveal: authenticate/origin/rate/strict body → begin/SQL deadlines → per-user advisory lock `hashtextextended('authored-student:'||userId,6)` → current problem parent FOR SHARE → exact permission FOR SHARE → validate approved solution/media → reuse/insert ledger → final expiry check → COMMIT → safe response.
- New attempt: the existing same user lock → original idempotency lookup → current parent FOR SHARE → existing grading/limits/insert/COMMIT. SQL0005's replacement attempt guard derives NEW.assisted with EXISTS(any own reveal on this revision) under that same lock. Client assisted fields remain rejected; no duplicate keys are stored.
- Attempt-first commits unassisted before the waiting reveal; reveal-first commits its event before the waiting attempt, which becomes assisted. The user lock also orders concurrent retries. An original committed idempotent attempt always replays its original selection/outcome/assisted flag, even after later help, unpublication or new publication. No old row is rewritten/regraded.
- Author permission writes lock parent FOR UPDATE **before** permission/binding mutations and never take a student advisory lock. Publish/unpublish and registry lifecycle use their existing parent-first order. Solution media GET takes parent SHARE → permission SHARE; its ledger is immutable, so no user lock is needed. No code path takes parent then waits for a student lock. Rate upserts finish outside these transactions.
- Trusted SQL metadata writers must follow the same parent-before-permission order; triggers do not replace application lock discipline. SQL guards enforce ownership/current publication/generation for grants, per-part media scope, immutable reveals/attempts and server-derived assistance. Tables are not exposed through generic clients/RLS tokens. No second pool connection is acquired while holding these locks; poolmax1 is tested.

## Additive migration and rollback

Apply `migrations/0005_authored_solution_access.up.sql` only in a separately authorized selected staging/release database, after0004 and using the existing [migration lock/checksum/source-commit ledger procedure](../../migrations/README.md). There is no startup/build/schema-push hook. **No shared or production migration is run in Phase6C-A.**

Creates permission, permission-media and immutable reveal tables with same-problem/revision/part FKs; immutable revision/private-key/media tables stay untouched. Mutable current permission metadata is separate from immutable worked solutions. Reveals retain their authorization-generation UUID without an FK to the mutable current generation, so revocation preserves history. User/revision-prefix index serves assistance; a separate authorization index keeps new-grant/revoke history checks bounded. No secret solution/key copies enter the ledger.

The only old-table change is dropping the false-only assisted CHECK and replacing the existing attempt guard to derive future flags. Existing flags/timestamps/results/ordinals/engine versions remain unchanged. no-reveal-v1 and submission metadata reveal="disabled" continue to describe **automatic grading disclosure**; the explicit endpoint has its separate policy. Shared client attempt schemas now accept a server boolean, preserving existing false receipts and newly assisted history.

Release sequencing must install0005 and the compatible server/client boolean contracts before author opt-in/student reveals are exposed. Ensure serving instances have completed the upgrade; old cached Phase6B tabs may need reload to accept assisted=true. Verify this in isolated staging at the later readiness gate, not by a production-tracked main commit.

Rollback exposure first. The down file refuses any permission/reveal or assisted attempt state; it does not erase audit/history. Empty new-table down/up with retained old unassisted attempts is tested, including exact old-record preservation. Do not edit/reapply already merged migrations0001–0004 or purge immutable work to force rollback.
