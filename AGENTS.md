## User experience and website copy (global rule)

- Prioritize usability over feature count. Keep pages, menus, forms and workflows simple. Do not add controls, explanatory cards, dashboards, badges, secondary options or extra steps merely because they are possible. Prefer simplifying, combining or removing low-value UI within the approved task scope.
- Design for someone visiting the site for the first time, without a tutorial or instructions from its developer. Each screen should make the next useful action clear through familiar labels, predictable navigation, concise context and meaningful feedback. Show success, loading, errors and recovery plainly. Use progressive disclosure only when it makes the task easier, not to hide essential information.
- Treat the end-to-end user journey as an acceptance criterion: entry point, finding the task, taking action, understanding the result and recovering from mistakes. Review at desktop and mobile widths and with keyboard navigation. Accessibility checks alone do not establish that a first-time user understands the flow.
- User-facing writing must sound natural, specific and direct. Avoid generic AI-sounding language, motivational aphorisms, dramatic slogans, vague subtitles, filler microcopy, inflated claims and decorative text that adds no information. Every heading, explanation and button should help the user understand or act.
- Do not use em dashes or semicolons in user-facing website copy. Prefer short sentences and ordinary punctuation. This restriction does not apply to programming syntax, data, mathematical notation, quoted source material or necessary technical/legal text.
- Never remove essential safety, permission, privacy, cost or error information just to make the page shorter. Preserve domain accuracy, especially for physics problems, solutions, grading and account operations.
- For each UI change, briefly justify what the user is trying to do, why the new interaction is necessary and whether a simpler version would work. Reject unnecessary complexity even when it is technically easy to implement. Do not expand the scope into an unrelated redesign.
